# Synthetic screen design record

The established design-taste-frontend app workflow from the v0.1 fixture project is reused: framed-sheet for office/operations apps, neutral terminal/editor chrome, IBM Plex Sans/Mono and Noto Sans/JetBrains Mono, and colour on operational status rather than ornamental KPI cards. The original app direction seed was 490575905. The bundled font choices remain fixed; this is an extension of the fixture system, not a new marketing page.

The user needs diverse desktop screenshots, not a functioning product or one uniform brand. Controls are intentionally inert and no phone layout is shipped. Names, magnitudes and objects are synthetic. These requirements override workflow advice about implementing real actions, one branded app and phone screens. Four compositions per application answer different questions: command output / journal / table / REPL; source / notebook / review / debugger; CI log / jobs / variables / release; headers / exchange / response / network; employee record / onboarding / directory / review; beneficiary / receipt / settlement / payout; query / tree / connection / import; secret / YAML / material / versions; support thread / timeline / case / attachment; trace / dialog / structured response / diagnostic dump.

The main design signature is the application's actual work object and its readable values. Several values on a screen belong to one inspection record. No photographic assets or generative image model are needed; exact text geometry is the priority. Source font sizes and themes are sampled independently to avoid a font/theme shortcut. All text colours and value styles are identical between sensitive and benign roles.

Quality evidence is fixture-specific: full DOM character geometry, ancestor clipping checks, actual loaded font faces, page errors, raster counterfactuals, native screenshots and contact sheets. The project does not claim a universal frontend inspector pass for forty inert fictional apps. Visual inspection logs and limitations are stored in `qa/visual_review.json` and `QUALITY_REPORT.md`.

An initial parallel-page production attempt failed the outside-box raster check on a CI screen. The same screen reproduced correctly in isolation. The incomplete attempt was discarded as a release candidate; production switched to one page with two animation frames after visibility changes. All final images must pass the same check. The failed attempt does not contribute images or labels to the final inventory.

Native visual review also caught a 32-hex-character SHA-256 prefix displayed without an explicit truncation marker in the material panel. Those thirty canonical screenshots were regenerated with a localized “truncated” label and ellipsis, with their dependent stress views recomputed. Turkish names were refined to a closed common-given-name list and generated surname parts before final QA. No model score informed either change.

The first full perceptual audit failed: the common office-app shell and large empty regions produced 1,383 cross-split pHash candidates, of which 1,084 met the secondary grayscale threshold. This was not dismissed as a numerical false alarm. Closest native pairs confirmed that several forms and panels were too similar. The initial report is retained as `qa/initial_similarity_audit.json`.

The four held-out application families were rebuilt as actual workbenches: a database menu/catalog/document system, a top-navigation material/version store, a three-pane support inbox with conversations and case properties, and four native failure modes (runtime overlay, desktop crash dialog, HTTP response plus diagnostics, compiler/source inspector). Body compositions changed along with the shells. No watermark, random barcode or split-indicating annotation was added to defeat the hash. Both arms retain identical styling; only the intended visible roles/values differ. The final full audit uses the SAME thresholds. Its result, including any remaining candidates and review, is authoritative in `QUALITY_REPORT.md`.

`--refresh-existing` is an internal development optimization used only with explicit per-layout render revisions during these repairs. Reproduction of the release should use the documented fresh `npm run generate` path; do not use the cache to apply arbitrary renderer-code edits.
